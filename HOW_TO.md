# Owner setup guide

This guide explains where each value in `.env.example` comes from and when you need it. Most settings are placeholders for features that are not implemented yet. **For the current Gate 0 PayPal runner, only the sandbox client ID and client secret are needed.**

## Start here

From the repository root:

```sh
cp .env.example .env
```

Put values only in `.env`. It is gitignored. Never paste secrets into source files, issues, chat, or the ignored `buildpack/` docs. If a secret is exposed, revoke/rotate it with its provider.

## Values in `.env.example`

| Variable | Where it comes from | Needed now? |
| --- | --- | --- |
| `PAYPAL_CLIENT_ID` | PayPal Developer Dashboard → **Apps & Credentials** → select **Sandbox** → create or select a REST app → copy its client ID. | **Yes**, for PayPal Gate 0. |
| `PAYPAL_CLIENT_SECRET` | Same sandbox REST app. Copy the secret and keep it private. PayPal shows the credentials on the app page. | **Yes**, for PayPal Gate 0. |
| `PAYPAL_ENV` | Set to `sandbox`. The Gate 0 script is sandbox-only and rejects a live setting. | **Yes**; leave as shown. |
| `PAYPAL_WEBHOOK_ID` | Created when registering a webhook URL for the same PayPal app. The ID is returned/displayed when the webhook subscription is created. | No. Wait until the webhook endpoint is implemented and reachable over HTTPS. |
| `DATABASE_URL` | A PostgreSQL connection URI supplied by your local PostgreSQL setup or database host. See [PostgreSQL connection strings](https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNSTRING-URIS). | No. Database code and schema are not implemented yet. |
| `ATTESTOR_PROVIDER` | A project decision: choose the model provider when implementing the semantic attestor. Examples include OpenAI and Anthropic; this repo has not selected one. | No. Do not create an API key yet. |
| `ATTESTOR_MODEL_ID` | The exact model identifier published by the selected provider. Freeze the choice before tuning/evaluation, as required by the build plan. | No. Set it after provider selection and attestor implementation. |
| `ATTESTOR_API_KEY` | Create a project-scoped API key in the selected provider’s developer console. For example, see [OpenAI API key help](https://help.openai.com/en/articles/4936850-where-do-i-find-my-openai-api-key) or [Anthropic API documentation](https://docs.anthropic.com/en/api/overview). API access and billing are separate from a consumer chat subscription; check the provider’s current account and billing requirements. | No. No AI provider is wired in yet. |
| `CARTATTEST_SERVICE_SIGNING_KEY` | Generated by the project owner when signed overrides/bundles are implemented. This is a private P-256 key, not a credential issued by PayPal or the AI provider. | No. Wait until the implementation defines the accepted key encoding and storage method. |
| `CARTATTEST_SERVICE_KEY_ID` | A stable name chosen by the project for the corresponding signing key, such as `demo-p256-v1`. It is a key label, not a secret. | No. The example value can remain until signing is implemented. |
| `DEMO_MODE` | A project runtime choice: `replay` for deterministic fixtures or `live` for connected services. | No. The current app does not read this setting yet. |

PayPal’s official [REST API getting-started guide](https://developer.paypal.com/api/get-started/) describes creating/selecting an app and copying its client ID and secret. Keep the dashboard set to **Sandbox** for this project’s characterization work. Do not put live credentials in `.env`.

## When the deferred values are needed

### PostgreSQL (`DATABASE_URL`)

When persistence work starts, install/run PostgreSQL locally or provision a database with the chosen host. Create a database and a dedicated user for CartAttest, then use the URI format:

```text
postgresql://USER:PASSWORD@HOST:PORT/DATABASE
```

The example in `.env.example` is only a local placeholder; it is not a provisioned database. URL-encode reserved characters in the username or password. Keep production database URLs in the deployment platform’s secret settings, not in a file.

### PayPal webhook (`PAYPAL_WEBHOOK_ID`)

First implement and deploy the webhook route at a public HTTPS URL. Then register that URL under the same PayPal REST app (Sandbox for development), select only the event types the implementation handles, and copy the returned webhook ID into `.env`. PayPal’s [webhook integration guide](https://developer.paypal.com/api/rest/webhooks/rest/) explains registration and verification. A webhook ID is associated with its app/environment, so keep sandbox and live values separate. Do not register a placeholder URL; the current repo has no webhook listener.

### Semantic attestor (`ATTESTOR_*`)

Before requesting an API key, decide which provider and structured-output-capable model the owner will use. Record the provider and exact model ID, review its data handling and pricing, and set a project budget if the provider supports it. Then create a project-scoped key in that provider’s console, save it directly into the local `.env`, and do not commit it. The attestor port exists, but there is no provider adapter yet.

### Signing key (`CARTATTEST_SERVICE_SIGNING_KEY`)

The owner generates this locally when the bundle/override signing code is ready; there is no external account that issues it. The design calls for P-256 / ES256. For reference, OpenSSL can generate a PEM key pair:

```sh
mkdir -p "$HOME/.config/cart-attest"
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:prime256v1 \
  -out "$HOME/.config/cart-attest/service-private.pem"
openssl pkey -in "$HOME/.config/cart-attest/service-private.pem" -pubout \
  -out "$HOME/.config/cart-attest/service-public.pem"
chmod 600 "$HOME/.config/cart-attest/service-private.pem"
```

Do not paste the PEM into `.env` until the implementation specifies whether it expects PEM text, a file path, or an encoded key. Keep the private key outside the repository, back it up securely, and configure the verifier with the matching public key through a separately pinned setting. `CARTATTEST_SERVICE_KEY_ID` should identify the key version; changing the key requires a new ID and a deliberate verifier update.

## What works today

The Gate 0 command loads `.env` and uses `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, and `PAYPAL_ENV`. Copy the sandbox credentials into `.env`, then run:

```sh
pnpm install
pnpm gate0 -- create path/to/cart-binding.json
```

The command creates a sandbox order and prints its approval URL. After approving it in the sandbox buyer account, use the returned order ID with the `get`, `capture`, and `patch` commands in [README.md](README.md). A patch file is a JSON array of PayPal JSON Patch operations; review it before running because it changes the named sandbox order. The other variables are currently documentary placeholders; adding them to `.env` does not configure features that have not been built.
